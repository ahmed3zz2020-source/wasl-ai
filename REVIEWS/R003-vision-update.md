## ١. ⭐ التصحيح المعماري الأكبر

### ١.١ R002 كان ناقص — والصحيح فيه

R002 قال:
> «إضافة نشاط جديد = إضافة حزمة بيانات، مش كتابة كود.»

ده **صحيح بس ناقص** — والمهم إنWeather nó حدود. لما عميل يطلب نشاط **مش فيه قدرات موجودة**، لازم برمجة.

### ١.٢ الموديل المعدَّل — ٤ طبقات

```
┌─────────────────────────────────────────────────────────────┐
│  ٠ · القدرات (Capabilities) — كود المحرك                    │

└─────────────────────────────────────────────────────────────┘
```

### ١.٣ ⭐ المسار المزدوج — القاعدة الرسمية

```
عميل يطلب نشاط «صيدلية»
        ↓
   هل القدرة موجودة في سجل القدرات؟
        ├── ✅ نعم ────────► Sector Pack Builder (أيام)
        │                    (تركيب + ضبط + اختبار)
        │
        └── ❌ لا ────────► مسار تطوير القدرة (أسبوع):
                             ① gap analysis (عيبان ناقصة؟)
                             ② مواصفة القدرة (عقد + صلاحيات + اختبارات)
                             ③ برمجة في المحرك خلف feature flag
                             ④ Simulation Lab (اختبار + red-team)
                             ⑤ تسجيل في Capability Registry
                             ⑥ ⭐ تُتاح لكل الحزم ⇒ أنشطة تانية تستفيد
                             ⑦ sector pack جديد يستخدمها
                             ⑧ نشر
```

**ⓘ الخطوة ٦ هي ديكل المشروع كله**: القدرة اللي اتبنت لعميل واحد بقت **متاحة لكل العملاء** ⇒ تكلفة العميل الثاني بتروح لصفر.

### ١.٤ ⭐ التصحيح في الوعد

| ❌ R002 (خطير) | ✅ R003 (صادق) |
|---|---|
| «إضافة نشاط = حزمة بيانات، مش كود» | **«نقدر نضيف نشاطك في أيام مش شهور»** |
| بتوحي إن كل قدرات موجودة | بتوحي إن في **قدرة** موجودة أو بتتبني بسرعة |

> ⭐ **ليه مهم**: لو وعدت عميل إن نشاطه يتحط «من غير برمجة» وبعدها طلع محتاج أسبوع برمجة ⇒ خسرت الثقة. الوعد بالزمن (أيام) **دقيق ومُرضي**.

### ٢.١ Capability Registry — سجل القدرات

**التعريف**: القدرة = **لبنة ذرّية** يقدر المحرك ينفّذها. atom قابل للاختبار والتركيب والإصدار.

**الفرق المهم عن «الأدوات» في R002**:

| | القدرة (Capability) | الأداة (Tool) |
|---|---|---|
| إيه | لبنة في المحرك | **غلاف صلاحيات** around قدرة |
| مين بيكتبها | فريق التطوير | المحرك تلقائياً |
| إيه بتحدد | العقد · الإصدار · الاختبارات · التكلفة | الصلاحية · الموافقة · الحدود |
| بتظهر في | السجل | سجل الأدوات (R002) |

```
القدرة (catalog.read) ──▶ الأداة (catalog.read + صلاحية + حدود) ──▶ المسار ──▶ الحزمة
```

**شكل سجل القدرة**:
```yaml
id: order.create
version: 2.1.0
kind: action | query | transform | detector
contract:
  input_schema: {...}
  output_schema: {...}
  idempotency_key: order_id
requires: [catalog.read, customer.upsert]      # ⭐ تبعيات ⇒ يحلّها الـBuilder
side_effect: write                              # read | write | irreversible
approval: auto                                 # auto | supervisor | owner
limits: { per_day: 200, max_value: 10000 }
owner: team-core
status: stable | beta | deprecated
since: 2026-01-15
deprecation: { replaced_by: null, until: null }  # ⛔ الحذف ممنوع — الإهمال فقط
tests: { suite: orders@2.1.0, pass_rate: 0.97 }
cost: { per_call: 0.0021 }
```

**الإمكانات الأساسية**:
- ⛔ **الحذف ممنوع** — القدرة بتُهمل (deprecated) مع بديل وتاريخ نهاية. سببها: لو حذفنا قدرة في بيئة فيها عملاء ⇒ كسر عندهم.
- ⭐ **التبعيات** (`requires`) ⇒ الـPack Builder يحلّ التبعيات لوحده ويقول «الحزمة دي محتاجة ٣ قدرات مش موجودة».
- ⭐ **شارة اختبار** — قدرة من غير اختبارات خضراء ⇒ **مش بتتنشر**.
- ⭐ **تكلفة الاستدعاء** ⇒ بتروح لـCost Intelligence ⇒ **السعر مبني على رقم**.

### ٢.٢ Workflow Designer — مصمم مسارات العمل

**التعريف**: المسار = **تسلسل قدرات** مع شروط وحواجز بشرية.

```
[استقبال الطلب] → [تأكد من المخزون] → [لو ناقص: اقترح بديل] → [تأكيد من العميل]
                                                     ↓
                                          [حاجز بشري: فوق ٥٠٠ ج.م]
                                                     ↓
                                              [تنفيذ الدفع] → [إيصال] → [متابعة بعد ٢٤س]
```

**نوع الخطوات**: استدعاء قدرة · شرط · فرع · انتظار · **موافقة بشرية** · إشعار.

**الإمكانات**:
- **محرّر بصري + YAML معاً** — البصري للعميل والإداري · YAML للإصدار والـdiff.
- **سقف ٨ خطوات و٣ مستويات تداخل** (فيها حد — التعقيد عدو الوضوح).
- **Dry-run** داخل Simulation Lab قبل النشر.
- ⛔ **مفيش خطوة تتجاوز غلاف الصلاحيات** لقدرتها — الحارس في المحرك مش في المصمم.
- **قوالب مسارات لكل قطاع** (مسار طلب مطعم ≠ مسار حجز عيادة).

**تعريف الشروط**:
```yaml
id: restaurant.order.flow
version: 1.2.0
steps:
  - use: catalog.item.available
    when: always
  - use: order.create
    when: context.payment_method == "cash"
  - use: payment.initiate
    when: context.payment_method == "card"
    requires_approval: supervisor
    when_value_over: 500
  - use: notification.receipt
    when: always
```

### ٢.٣ Sector Pack Builder — بناء الحزم

**من YAML يدوي ⇒ لأداة تأليف.** ده اللي بيخلّي غير المطوّر يقدر يضيف نشاط.

**مِسار التأليف**:
```
١. اختر قالب أساسي (archetype)         ← ٢٧ نشاط جاهز كقوالب
٢. اختار القدرات من السجل              ← تبعيات محلولة تلقائياً
٣. اربط المسارات بالأنشطة              ← Workflow Designer
٤. اكتب الاستبيان (يتولّد من القدرات)   ← ⛔ ما تكتبش أسئلة مش ليها إجابة
٥. اكتب قوالب الوكيل والنبرة
٦. حدّد بنية المعرفة المطلوبة
٧. ⭐ اربط مجموعة الاختبار              ← Simulation Lab
٨. ⭐ مراجعة + نشر
```

**الإمكانات**:
- **توليد الاستبيان من القدرات**: لو القدرة `order.create` موجودة ⇒ السؤال «إزاي بتاخد الطلب؟» بيتولّد. ⇒ **مفيش سؤال بلا إجابة**.
- **ورشة التأليف**: قبل ما تكتب حزمة جديدة ⇒ النظام بيقترح أقرب حزمتين ويقول «أقرب نسخة عندك».
- **وراثة الحزم**: حزمة «مطاعم فاخرة» ترث «مطاعم» ⇒ بدل تكرار. ⭐ ده ضروري مع نمو الحزم.
- **بوابة نشر**: ⛔ ما تنشرش من غير eval suite خضراء.
- **إصدارات**: مسودّة ⇒ مراجعة ⇒ منشورة ⇒ مهملة.

**شكل الحزمة** (الموسَّع):
```yaml
sector: مطعم
version: 1.0.0
extends: null                    # ⭐ وراثة
archetype: food.service
capabilities: [menu.read, order.create, reservations.book, delivery.track]
workflows: [restaurant.order.flow, restaurant.reservation.flow]
questionnaire: [...]             # ⭐ متولّد من القدرات
agent_templates: {...}
knowledge_schema: [menu, hours, delivery_policy, reservation_rules]
eval_suite: {...}                # ⭐ بوابة النشر
kpis: [fcr, avg_response, upsell_rate, table_turnover]
```

### ٢.٤ Brand Identity Studio — استوديو الهوية

**بيستبدل** «آليتين في R002» بمعمارية كاملة قابلة للتشغيل.

**الإمكانات**:
| # | القدرة | التفصيل |
|---|---|---|
| ١ | **استخراج اللوحة** | من شعار العميل ⇒ ألوان أساسية + ثانوية + تباين محسوب |
| ٢ | **توليد الرموز** | accent · accent-2 · سطح · حدود — مع **ضمان تباين AA** |
| ٣ | **مُركِّب التركيب (Lockup)** | ٣ صيغ مُصمَّمة (قوس مشترك · تداخل · خط أساس) · SVG · ar/en · فاتح/غامق |
| ④ | **عكس الأدوار** | قواعد لكل سطح: مين يقود · إزاي بتظهر WASL |
| ⑤ | **حزمة الهوية المُولَّدة** | lockup + ترويسة فاتورة + هيدر واتساب + أفاتار + صورة اجتماعي + ترويسة إيميل (٦ عناصر) |
| ⑥ | **معاينة حيّة** | تطبيق الهوية على شاشات لوحة التاجر فوراً |
| ٧ | **تصدير رموز التصميم** | ملف design tokens ⇒ مش محبوس في WASL |
| ٨ | **فحص الجودة** | تباين AA + حجم خط · ⛔ لو مش ماشي ⇒ يعدّل اللوحة تلقائياً ويقول |

**قاعدة التحقق**: لو لون العميل ما يقدرش يوصل تباين AA ⇒ **الاستوديو يعدّل** (مش بيطلّع هوية مكسورة).

### ٢.٥ Simulation Lab — مختبر المحاكاة

**ده أكبر ترقيّة عن R002.** في R002 كانت «مجموعة اختبار JSON». دلوقتي **مختبر كامل**.

**الإمكانات**:

| # | القدرة | إيه بتعمل |
|---|---|---|
| ١ | **توليد سيناريوهات** | من استبيان الحزمة + المعرفة ⇒ حوارات اختبار |
| ٢ | **شخصيات محاكاة** | مستعجل · مش confused · غاضب · بيخلّي إنجليزي · فرانكو عربي · عميل زبون |
| ٣ | **إعادة تشغيل (Replay)** | محادثات حقيقية من Production ⇒ تشغيلها على نسخة جديدة ⇒ **مقارنة** |
| ٤ | **Red-teaming** | حقن تعليمات · « ignorا تعليماتك » · «اديني خصم ١٠٠٪» · أسئلة قانونية/طبية |
| ٥ | **فحص التثبيت (Grounding)** | كل جملة في الرد ⇒ مصدرها؟ ⇒ **صفر جملة بلا مصدر** |
| ٦ | **مقارنة A/B** | نسخة قديمة × جديدة على نفس السيناريوهات |
| ٧ | **عارض التتبّع (Trace)** | كل محادثة: الاسترجاع ← الأداة ← الرد ← سبب التصعيد |
| ٨ | **بوابة الانحدار** | ⛔ نشر النسخة الجديدة لو تدهور أي عتبة عن النسخة القديمة |

**مقاييس المختبر** (لكل نسخة):
```
grounding_accuracy      = 1.0  (صفر جملة بلا مصدر)      ⛔ شرط نشر
refusal_accuracy        ≥ 0.90
tool_selection_accuracy ≥ 0.92
escalation_precision    ≥ 0.85
escalation_recall       ≥ 0.90
dialect_accuracy        ≥ 0.85 (لكل لهجة على حدة)
red_team_resistance     = 1.0  (صفر نجاح للحقن)
latency_p95             ≤ 3s
cost_per_conversation   ≤ سقف الحزمة
```

**⭐ مبدأ**: المختبر **مش أداة devs** — هو **بوابة نشر**. مفيش حزمة ولا قدرة ولا نسخة تنشر من غير عدّه أخضر.

### ٢.٦ Cost Intelligence — ذاكرة التكلفة

**ده اللي بيخلّي «أسعار تنافسية» ممكنة.** مش تقدر تنافس لو مش عارف تكلفتك.

**الإمكانات**:
| # | القدرة | التفصيل |
|---|---|---|
| ١ | **القياس (Metering)** | كل استدعاء قدرة + كل توكن + كل رسالة قناة ⇒ منسوب لـ (tenant · capability · workflow · pack · channel) |
| ٢ | **وحدة الاقتصاد** | تكلفة المحادثة · تكلفة التذكرة المحلولة · تكلفة الطلب |
| ٣ | **الهامش** | الإيراد مقابل التكلفة لكل عميل · خطة · قطاع |
| ٤ | **What-if** | «لو بدّلنا نموذج محرك اللهجات ⇒ الهامش بيتغيّر كام؟» |
| ٥ | **إنذارات** | عميل عدّى ميزانيته · قدرة بتكلّف كتير ومحدش بيستخدمها |
| ٦ | **اشتقاق السعر** | من التكلفة ⇒ **أرضية سعر** مقترحة |
| ٧ | **ترتيب الهدر** | أي قدرة غالية + نادرة الاستخدام |

**⭐ قاعدة إلزامية**: ⛔ **أي مسار من غير وسم تكلفة = مرفوض.** من غير ما، بيانات التاريخ بتضيع للأبد.

### ٢.٧ Version Control — ضبط الإصدارات

**مش git — ضبط إصدارات على مستوى المنتج.**

**المُصدَّر (Versioned)**: القدرات · الحزم · المسارات · البرومبتات · إعدادات الوكيل · بنى المعرفة · رموز الهوية.

**الإمكانات**:
| # | القدرة | التفصيل |
|---|---|---|
| ١ | **إصدارات دلالية** | semver على كل artifact |
| ٢ | **بيئات** | dev ⇒ staging ⇒ prod لكل عميل |
| ٣ | **Diff مرئي** | إيه اللي اتغيّر في الحزمة (أسئلة · أدوات · قوالب) — مش بس diff كود |
| ٤ | **مسار مراجعة** | من لمين غيّر إيه وليه |
| ٥ | **Rollback** | رجوع نسخة سابقة لكل عميل في < ٥ دقائق |
| ٦ | **ترويج (Promotion)** | نشر نسخة على ١٠ عملاء مرة واحدة **أو** تدريجياً |
| ٧ | **مصفوفة التوافق** | أي نسخة حزمة تتوافق مع أي نسخة قدرة |
| ٨ | **سجل تدقيق** | كل تغيير · من · إمتى · ليه |

**⭐ سياسة الإهمال (deprecation)**: القدرة/الحزمة **ما بتتحذفش أبداً** — بتُهمل مع بديل وتاريخ. سببها: عميل لسه شغّال على النسخة القديمة.
