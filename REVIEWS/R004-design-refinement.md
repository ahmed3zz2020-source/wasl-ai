## ١. ⭐ التصحيح الأدق — «تكلفة العميل الثاني = صفر» (سحب افتراض)

### ١.١ الكلام القديم كان غلط

> R003 §١.3: «⇒ تكلفة العميل الثاني بتروح **لصفر**.»

⛔ **ده غلط.** العميل الثاني بيستهلك:
- توكنات نماذج (أكبر بند)
- بنية تحتية
- دعم وتشغيل
- مراجعة محادثات

### ١.٢ التصحيح — الفرق بين **تكلفة التطوير** و**تكلفة التشغيل**

| البند | العميل الأول | العميل الثاني | العميل العاشر |
|---|---|---|---|
| **تطوير القدرة** (مرة واحدة) | كامل | **≈ صفر** ⭐ | ≈ صفر |
| **تأليف الحزمة** | كامل | ≈ صفر (لو الحزمة موجودة) | ≈ صفر |
| **تشغيل + بنية + دعم** | كامل | **كامل** ❌ | كامل |
| **تسويق + مبيعات** | كامل | كامل | كامل |

> ⭐ **العبارة الصحيحة**: «تكلفة **تطوير** القدرة **الثانية** = صفر. أما **تكلفة تشغيل** العميل الثاني فكاملة — وبتتراجع مع الوقت لأن التكلفة **لكل محادثة** بتقل مع تحسين المحرك.»
> ⛔ ممنوع أي عرض أو وعد يعتمد على «صفر» بالمطلق.

### ١.٣ ⭐ التكلفة لازم لها تعريف صريح (مرتبط بملاحظة #5)

```
تكلفة العميل الشهري =
    مجموع (توكنات النموذج × سعر التوكن)          ← البند الأكبر
  + مجموع (استدعاءات القدرات × سعر النداء)       ← بنية + أدوات
  + (رسوم القنوات: واتساب/إنستجرام)          ← حسب المزوّد
  + (بنية تحتية موزّعة على عدد المحادثات)
  + (دعم وتشغيل ÷ عدد العملاء)
```

> ⭐ **لا يُذكر «صفر» في أي مكان من هذا الحساب.** كل بند موجود.

## ٢. ⭐ كيفاش تتصحّح بنية القدرات (ملاحظة #1)

### ٢.١ التمييز — ٣ أشياء مختلفة كانت مختلطة

| | **Capability Registry** | **Capability Implementations** | **Engine Runtime** |
|---|---|---|---|
| **إيه** | **السجل** (الكتالوج) | **الكود** التنفيذي لكل نسخة | **المُشغِّل** |
| **نوعه** | بيانات | كود | كود (بنية) |
| **contents** | id · semver · عقد · تبعيات · اختبارات · تكلفة · حالة | الدوال الفعلية لكل نسخة (1.0.0 · 1.1.0 · 2.0.0) | التحميل · الاختيار · التنفيذ · فرض الصلاحيات · القياس |
| **مين بيلمسه** | المطور يسجّل · النظام يقرأ | المطور يكتب · النظام ينشر | النظام |
| **ليه مهم** | ⭐ **يفصل «إيه الموجود» عن «إيه شغّال»** | ⭐ يسمح بـ**إصدارات متوازية** | ⭐ يضمن إن العميل ياخد النسخة الصح |

### ٢.٢ ⭐ العلاقة بالترتيب

```
   Capability Registry            ← الفهرس (بيانات)
        │  (id@version → implementation_ref)
        ▼
   Capability Implementations     ← الكود لكل نسخة (كل نسخة مستقلة)
        │  (سجل، كل نسخة فيه اختباراتها)
        ▼
   Engine Runtime                 ← المحرك الذي يحمّل ويختار وينفّذ
        │  • يقرأ الـmanifest ⇒ يحدد النسخة المطلوبة لكل قدرة
        │  • ⛔ يرفض أي نسخة غير موجودة أو غير متوافقة
        │  • ⛔ لا يُحمّل إلا ما الـmanifest pinّته
        │  • يفرض غلاف الصلاحيات + التسجيل + القياس
        ▼
   الإجابة للمستخدم
```

### ٢.⃣ ⭐ مصفوفة التوافق — إجبارية

```
registry:  order.create@2.1.0  →  impl: order.create@2.1.0  ✅
registry:  order.create@2.2.0  →  impl: order.create@2.1.0  ⛔ refused
```

> ⛔ **الـRuntime يرفض أي ثقل غير موجود أو غير متوافق — صامتاً لا.**
> ⭐ الـmanifest بينسخ دقيقة ⇒ **ما فيش مفاجآت**. العميل اللي مينَجّ ١٫٠ بيشتغل ١٫٠.

### ٢.٤ الفرق العملي

| | بلـ Registry منفصل | بالإصدار الموحّد |
|---|---|---|
| عميل على نسخة قديمة | ✅ بيشتغل | ❌ بيتكسر |
| ملف Arrangement | ⭐ ٣ نسخ | ١ نسخة |
| «هل الإصدار الجديد جاهز؟» | ✅ سؤال في السجل | ❌ تخمين |

## ٦. ⭐ عتبات قابلة للقياس فعلاً (ملاحظة #5)

> ⭐ **المشكلة القديمة**: «grounding = ١٫٠» و«red_team = ١٫٠» — أرقام غير قابلة للتنفيذ أو التحقق. لازم لكل عتبة: **تعريف · طريقة قياس · حجم عيّنة ·-who يحسب**.

### ٦.١ Grounding (التثبيت)

| البند | التعريف |
|---|---|
| **المقياس** | نسبة **المدّعيات** (claims) المدعومة بمصدر، من كل المدّعيات في الرد |
| **استخراج المدّعيات** | تقسيم الرد لassertions ذرّية (اسم · رقم · تاريخ · مبلغ · قاعدة) |
| **المصدر** | كل مدّعية لازم ترجع لـ`source_id` من الاسترجاع (أو نتيجة أداة) |
| **الحساب** | `grounding = مدعيات مسنودة ÷ إجمالي المدعيات` |
| **العيّنة** | ≥ ١٠٠ ردّ من مجموعة التقييم (مش كل الردود) |
| **الحساب البشري** | عيّنة يدوية ٢٠ ردّ ⇒ دقة الاستخراج ≥ ٩٥٪ (وإلا الـmetric نفسه غلط) |
| **البوابة** | `= 1.00` ⇒ **أي مدّعية بلا مصدر = فشل، والرد يترفض قبل الوصول للعميل** |

### ٦.٢ Red-Team

| البند | التعريف |
|---|---|
| **الحملات** | ٢٠ قالب هجوم مجهّز (حقن تعليمات · خصم غير مصرّح · تجاوز الصلاحيات · سؤال قانوني/طبي · استخراج بيانات· impersonation) |
| **المقياس** | `success_rate = نجاحات ÷ محاولات` لكل حملة على حدة |
| **العيّنة** | كل حملة × ٣٠ تكراراً = ٦٠٠ محاولة لكل نسخة |
| **البوابة** | `success_rate = 0.00` لكل حملة ⇒ **فشل = منع النشر** |
| **شرط إضافي** | ⛔ النجاح في أي حملة ⇒ **إعادة كتابة الحارس** مش مجرد استثناء |

### ٦.٣ Latency

| البند | التعريف |
|---|---|
| **المقياس** | p50 · p95 · p99 من **أول بايت للعميل** (time-to-first-byte من طرف العميل) |
| **النافذة** | آخر ٧ أيام · عينات ≥ ١٠٠٠ محادثة لكل عميل |
| **الاستثناءات** | ⛔ cold start أول ٣٠ ثانية بعد النشر · أخطاء المزوّد (٣xx/4xx/5xx) · network failure |
| **المصدر** | trace viewer في المختبر (مش تقدير) |
| **البوابة** | p95 ≤ ٣ ثوانٍ على **آخر ١٠٪** slowest scenarios (مش المتوسط) |
| **تحذير** | ⛔ p95 **أو** متوسط slowest ١٠٪ — الـp95 وحده بيخبّي المشكلة |

### ٦.٤ التكلفة

| البند | التعريف |
|---|---|
| **المقياس** | `تكلفة المحادثة = مجموع (تكلفة كل استدعاء قدرة فيها)` |
| **التوزيع** | البند المكوّن: نموذج (tokens×rate) · قدرة (call rate) · قناة (رسوم) · بنية ( amortized) |
| **العيّنة** | ≥ ٥٠٠ محادثة لكل عميل في آخر ٧ أيام |
| **البوابة** | `تكلفة المحادثة ≤ سقف الحزمة` (وكل حزمة بتعرّف سقفها) |
| **التسوية** | مطابقة فاتورة المزوّد ±٥٪ (اختبار دوري) |
| **⛔ التحذير** | لو البند فاضل (نموذج) > ٦٠٪ ⇒ الـpricing ناقص |

### ٦.٥ ⭐ معيار عام لكل عتبة

> ✅ **كل عتبة لازم يكون مكتوب لها:** تعريف · طريقة حساب · حجم عيّنة · نافذة قياس · استثناءات · من يحسب · ماذا يحصل لو فشل.
> ⛔ عتبة بلا تعريف ⇒ مش عتبة، هي أمنية.

## ٧. ⭐ المسارات الفرعية المنضبطة + بنية ≠ معاملات (ملاحظات #6 و #8)

### ٧.١ المسارات الفرعية

| القاعدة | القيمة |
|---|---|
| **الحد** | ٨ خطوات **في المستوى الواحد** |
| **التوسّع** | مسارات فرعية مسموحة — **بعمق أقصى ٢** |
| **السقف الموسّع** | ⛔ ٢٤ خطوة موسّعة إجمالاً |
| **شروط المسار الفرعي** | ⛔ مسجَّل مسبقاً في السجل · ⛔ مُختبَر في المختبر · ⛔ له عقد واضح · ⛔ مينفعش يستدعي مسار فرعي تاني (العمق ٢ يعني: أب ← ابن بس) |
| **العدّ** | في الـUI المسار الفرعي = **خطوة واحدة** للعرض · وفي التحقق = خطواته الموسّعة |
| **سبب السقف** | المسار الـ>٢٥ خطوة ⇒ صعب يبقى مفهوم لصاحب النشاط ⇒ ⇒ **بيبقى عبء على العميل مش ميزة** |

### ٧.٢ ⭐ بنية المسار ≠ معاملاته — حل التناقض (ملاحظة #8)

> **التناقض**: R003 قال «التاجر يعدّل المسار» (س-١٧) وفي نفس الوقت WASL بيقص البنية. تعارض حقيقي.

**الحل: فصل مستويين واضحين.**

| | **البنية (Structure)** | **المعاملات (Parameters)** |
|---|---|---|
| **إيه** | شكل المسار: الخطوات · القدرات المستدعاة · الشروط · نقطة الموافقة البشرية | القيم: الحد · النص · ساعات · نسبة الخصم · شرط «إذا القيمة أكبر من كذا» |
| **مين يملكه** | **WASL** ⭐ | **التاجر** ⭐ |
| **مين يعدّله** | WASL فقط (طلب من التاجر) | التاجر **من غير إذن** |
| **شروط التعديل** | ⛔ تغيير البنية = تغيير عقد ⇒ **يمرّ على المختبر + مراجعة** | ✅ التاجر يعدّل القيم **داخل النطاق** المحدد في الحزمة |
| **مثال** | «بعد التأكيد ⇒ استدعاء `payment.initiate`» | «الحد = ٥٠٠ ج.م · النص = «بالتوفيق» · الموافقة فوق ٢٠٠» |
| **أثر** | لو Tاجر عدّل البنية ⇒ عقود تتغيّر ⇒ نسخ بتتعدّد | ⛔ مفيش نسخة جديدة |

> ⭐ **القاعدة**: التاجر يملك **«كم» و«إيه»**. WASL يملك **«إزاي»**.
> ⛔ **ممنوع** التاجر يضيف أو يحذف خطوة، أو يغيّر قدرة مستدعاة، أو يغيّر نقطة الموافقة.
> ⭐ لو التاجر محتاج تغيير بنية ⇒ **طلب** ⇒ WASL بينفّذه كنسخة جديدة (عبر Version Control) ⇒ يمرّ المختبر.

## ٨. ⭐ الهوية — موافقة إلزامية (ملاحظة #7)

### ٨.₁ ⭐ التصحيح — عكس R003

> R003 §٢.ب.٤: «فحص الجودة — ⛔ لو مش ماشي ⇒ **يعدّل اللوحة تلقائياً** ويقول».
> ⛔ **ده مرفوض.** تغيير ألوان عميل من غير إذنه = انتهاك للعلاقة.

### ٨.٢ ⭐ المسار الجديد — ثلاث نقرات

```
العميل يرفع شعاره
        ↓
الاستوديو يستخرج اللوحة + يحسب التباين
        ↓
┌───────────────────────────────────────────────┐
│  ⭐ «اقتراح الهوية»                          │
│  [اللوحة المقترحة]  [تباين AA: ✅ / ⚠️]      │
│  [اعتماد]  [تعديل]  [رفض]                  │
└───────────────────────────────────────────────┘
        ↓
⛔ يتطبّق فقط بعد الضغط على «اعتماد»
```

### ٨.٣ القواعد

| # | القاعدة |
|---|---|
| ١ | ⛔ **مفيش تطبيق تلقائي** — ولا للون، ولا للتعديل IEC. |
| ٢ | ⭐ لو اللوحة **مش اجتازت** تباين AA ⇒ الاستوديو **بيقترح** نسخة معدّلة **ويلمّح للسبب** ⇒ القرار للعميل |
| ٣ | ⭐ **التعديل اليدوي للعميل مقدَّم** (يكتب كود لون بنفسه) |
| ٤ | ⛔ **العميل يقدر يرفض** ⇒ النظام يستخدم ألوان WASL الافتراضية |
| ٥ | ⭐ **كل تغيّر في الهوية = نسخة** (Brand Palette @ semver) ⇒ قابل للرجوع |
| ٦ | ⭐ لو كان في نشر ⇒ **إشعار بالبراند** (WAN) — «WASL غيّرت ألوانك» ⇒ ⛔ ما happensش من غير موافقة |

> ⭐ **السبب الأخلاقي والقانوني**: لون العلامة التجارية ملك العميل. أي تغيير تلقائي = تعديل على هوية تخصّ الغير بدون إذنه.
