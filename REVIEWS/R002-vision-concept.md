## ٣. المعمارية المقترحة

### ٣.١ ⭐ الفكرة المعمارية المركزية: ثلاث طبقات

> **«إضافة نشاط جديد = إضافة حزمة بيانات، مش كتابة كود.»**

ده هو الشرط اللي يخلي الرؤية ممكنة economically. لو كل عميل = كود جديد ⇒ تكلفة بناء + صيانة + استحالة التوسّع.

```
┌─────────────────────────────────────────────────────────────┐
│  ١ · المحرك (Engine) — كود يُكتب مرة واحدة                  │
│  runtime الوكيل · محرك المعرفة · سجل الأدوات · الصلاحيات   │
│  نظام التصميم · i18n · محرك اللهجات · القياس               │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│  ٢ · حزمة القطاع (Sector Pack) — بيانات لكل نشاط           │
│  استبيان الإعداد · قوالب الوكيل · مجموعة الأدوات           │
│  قوالب السياسات · مجموعة الاختبار · مؤشرات الأداء          │
│  ⬆ versioned · تنزل بالبيانات مش بنشر كود                  │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│  ٣ · إعداد العميل (Tenant Config) — بيانات لكل عميل         │
│  المنتجات والأسعار · السياسات · أوقات العمل · النبرة        │
│  اللغة · الصلاحيات · الهوية البصرية · خطة الاشتراك          │
└─────────────────────────────────────────────────────────────┘
```

**لماذا هذا يحل التناقض الظاهري**:
- «العميل يحس إن WASL مخصوص لنشاطه» ✅ ⇒ لأن حزمةقطاعه + إعداداته حقيقية ومختلفة.
- «مش هنكتب كود لكل عميل» ✅ ⇒ لأن الكود واحد، والاختلاف **بيانات**.
- «نضيف نشاط» ⇒ **حزمة** بتُؤلَّف وتُختبَر وتُنشر. مش deploy.

**الدليل على الجدوى**: كلزمة قطاع = ملف JSON/CSV + نصوص + مجموعة اختبار. تتضاف للـDB بـupsert. الـengine يقراها وقت التشغيل. **صفر نشر.** ده بيلغي أكبر عائق في «منصة تخدم كل الأنشطة».

### ٣.٣ العزل بين العملاء (Multi-tenancy)

**القرار المقترح**: **Postgres واحد + `tenant_id` على كل جدول + Row-Level Security**.

**ليه مش ملف لكل عميل**: لوحة الإدارة المركزية محتاجة تجميع على مستوى المنصة (أداء · تكاليف · اشتراكات) — دي مستحيلة عملياً مع عزل فيزيائي كامل. وكمان الـanalytics والـbilling بيتكلم مع كل الـtenants.

**ليه مش صفحة لكل عميل**: تشغّل وصيانة مكلفة + SQLite عنده قيود (مافيش RLS حقيقي · كتابة متزامنة وحيدة).

**ليه RLS مش بس فلتر في الكود**: لو الفلتر نسيه في استعلام واحد ⇒ تسريب بيانات عميل لعميل. RLS = الـقاعدة نفسها ترفض ⇒ خطأ برمجي **مش** ثغرة أمنية.

**حارس إلزامي (release gate)**: مجموعة اختبارات عدائية — ٥٠ محاولة وصول متعمّدة من tenant A لـtenant B ⇒ ٠ تسريب. الاختبار ده **بيمنع النشر** لو فشل.

**مسار الإقامة الجغرافية**: الـRLS بيفصل logical. لو عميل خليجي طلب data residency ⇒ بـننقل الـDB كله لـinstance في المنطقة (مش tenant واحد). لو عميل طلب عزل فيزيائي ⇒ dedicated instance. **التصميم يسمح بالقotropiches للاعتماد، وبيتحدد مع أول عقد.**

```
رسالة العميل
   ↓
[١] تطبيع النص + كشف اللهجة + فرانكو + خلط لغات
   ↓
[٢] استخراج النية + الكيانات (اسم · منتج · تاريخ · مبلغ)

   ↓
```

**مبدأ صارم — منع الاختراق (منRequirement الصريح)**:
> كل معلومة في الرد لازم مصدرها **إما** معرفة النشاط **إما** نتيجة أداة **إلا** ⇒ يرفض ويحوّل.
> ده **مفروض** في الكود مش في الـprompt بس.

**ضمان عملي**: كل إجابة بتتحقق آلياً (grounding check) قبل ما تطلع. لو مفيش مصدر ⇒ مسار الرفض + التصعيد.

### ٣.٦ نظام الأدوات والصلاحيات

**كل أداة تعلن four things**:
```ts
{
  id: 'orders.create',
  scope: 'orders.write',          // الصلاحية المطلوبة
  side_effect: 'write',          // read | write | irreversible
  approval: 'auto',               // auto | supervisor | owner
  limits: { per_day: 100, max_value: 5000 },
  audit: true
}
```

**نطاقات الصلاحيات**: `catalog.read` · `catalog.write` · `orders.create` · `orders.refund` · `appointments.book` · `customers.read` · `customers.write` · `payments.initiate` · `agent.config` · `staff.invite` · `branding.edit` · `reports.read` · `settings.billing`

**الأدوار**: `owner` (كل حاجة) · `admin` · `supervisor` (يعتمد التصعيدات والاسترجاع) · `agent_viewer` (قراءة المحادثات فقط) · `analyst` (تقارير فقط)

**قاعدة التصميم**: الموظف الذكي **يقترح** الأداة دايماً. الـruntime هو اللي بيتحقق ويوافق ويرفض ويسجّل. ⛔ الأداة ما تقدرش تنفّذ نفسها.

| ١٠ | **التكاملات** | WhatsApp · بوابات الدفع · CRM · محاسبة |
| ١١ | **سجل التدقيق** | كل إجراء · من · متى · ماذا · النتيجة |
| ١٢ | **مفاتيح الميزات** | تشغيل/إيقاف تدريجي |
| ١٣ | **الدعم** | تذاكر · مالك كل حساب · حالة الخدمة |

**متطلبات خاصة**:
- ⛔ **عالم مصادقة منفصل** عن merchants — حساب واحد بـ«saw everything» = خطر.
- ⛔ **كل شاشة حسّاسة** (tenant data · مفاتيح · استرجاع) ⇒ تأكيد + تسجيل.
- **زمن الوصول ٥٠ms** للوحة ⇒ Pages + API cache.

## ٥. نظام القطاعات والأنشطة — وإضافة نشاط جديد

### ٥.١ النموذج

**حزمة القطاع** = حزمة بيانات مُصدَّرة (versioned)، مكوّنها:

```yaml
sector: مطعم
version: 1.0.0
questionnaire:        # أسئلة معالج الإعداد
  - id: cuisine
    q: نوع المطبخ؟
    type: choice
    options: [فاست, مشاوي, بحري, مقهى, متنوع]
  - id: avg_ticket
    q: متوسط قيمة الفاتورة؟
    type: number
    help: بصّ على آخر ١٠ فواتير
tools: [menu.read, orders.create, reservations.book, delivery.track]
agent_templates:
  greeting: "أهلاً بيك في {restaurant}. تحب أطلبلك ولا تحجز طاولة؟"
  tone: ودود ومختصر
  escalation: [طلب كبير, شكوى جودة, طلب خصم]
knowledge_templates:   # بنية المعرفة المطلوبة
  - menu
  - opening_hours
  - delivery_policy
  - reservation_rules
eval_suite:
  - q: "فين أكل؟"              expect_from: knowledge.menu
  - q: "عايز أطلب بيتزاPepperoni" expect_action: orders.create
  - q: "القاهرة بتاعة كام؟"     expect_from: knowledge.delivery_policy
kpis: [fcr, avg_response, upsell_rate, table_turnover]
```

### ٥.٢ ⭐ دورة «إضافة نشاط جديد» — بدون كود

```
١. تعريف النشاط       → قائمة المناطق (٢٧ نشاط: مطاعم · عيادات · متاجر · ...)
٢. تأليف الحزمة       → استبيان + أدوات + قوالب + معرفة + اختبارات
٣. اختبار الحزمة      → ٥٠ سؤال × حد أدنى ٨٥٪ دقة
٤. مراجعة             → المالك يعتمد
٥. النشر              → upsert في DB — ⭐ بدون deploy
٦. التفعيل             → النشاط يظهر في لوحة Central Admin
٧. التوسّع للعميل     → العميل يختاره من المعالج
```

**الأثر على الكلفة**: إضافة نشاط تاني = **يومان عمل** (تأليف + اختبار)، مش أسبوع برمجة. ⭐ ده اللي بيمكّن «يخدم جميع الأنشطة».

**الحزم المقترحة للترتيب** (بموافقة المالك):
`مطاعم · متاجر إلكترونية · عيادات · صيدليات · شركات خدمات · عقارات · مدارس ·PDAT`

### ٥.٣ ⭐ Guardrails ضد «حزمة ضعيفة»

| الخطر | الحارس |
|---|---|
| حزمة من غير اختبار | ⛔ ما تنتشرش من غير `eval_suite` كامل |
| حزمة من غير معرفة كافية | ⛔ wizard يرفض التفعيل لو المعرفة ناقصة |
| عميل يطلب نشاط مش موجود | ⛔ «نقدر نضيفه — محتاج ٣ أيام تأليف + اختبار» + عرض سعر |
| تكرار الحزم | ⛔ ورشة تأليف: نشوف اللي موجود ونزوّد عليه بدل ما نعمل من الصفر |

## ٨. Co-Branding — حلول إبداعية (مش شعارين جنب بعض)

### ٨.١ ⭐ المشكلة الحقيقية

«WASL» + «شركة العميل» جنب بعض = **شعارات**. المطلوب: **هوية مشتركة** ⇒ العميل يحس إن WASL جزء من مؤسسته.

**الحل: تبديل طبقي للهوية، مش تكديس.**

### ٨.٢ ٥ آليات

**ⓐ — اللون التكيّفي (Adaptive Accent)** — الأساس
> نظام تصميم WASL بيعرّف tokens. العميل يرفع شعاره ⇒ **نستخرج لوحة ألوانه** ⇒ الـaccent كله في اللوحة بيتغيّر.
> النتيجة: اللوحة **بتشكلها** شركة العميل — مش WASL حاطّة لوجو.

**ⓑ — تركيبة مُصمَّمة (Designed Lockup)** — مش صورتين
> ٣ صيغ مُصمَّمة (مش حط شعارين):
> ① **القوس المشترك**: قوس واحد يحتضن العلامتين.
> ② **التداخل**: علامة العميل جوه حاوية WASL.
> ③ **خط الأساس**: العلامتان على خط مشترك + فاصل.
> كل صيغة **مكوّن** واحد بيتولّد في كل مكان: الدخول · الترويسة · الإيميل · الفاتورة · قالب واتساب · الكود.

**ⓒ — عكس الأدوار حسب السياق (Role Reversal)** ⭐ الأهم
> | السطح | مين يقود | إزاي بتظهر WASL |
> |---|---|---|
> | **لوحة العميل** · محادثات عملائه · فواتيره · إيميلاته | **العميل** | شارة «مدعوم بـ WASL» بخفة، بلون العميل |
> | **لوحة المنصة** · صفحات قانونية · تسويقية | **WASL** | العملاء كقائمة |
>
> ده بالظبط «الفخر بظهور اسمه بجانب WASL» — **من غير ما يتنافسوا على المساحة**.

**ⓓ — حزمة هوية مُولَّدة (Generated Identity Kit)**
> عند التجهيز، النظام يولّد **بComplete حزمة** من قوالب WASL + شعار العميل + لوحته:
> - lockup SVG بالعربية والإنجليزية
> - أيقونة وأفاتار (للموظف الذكي)
> - ترويسة إيميل
> - هيدر قالب واتساب
> - هيدر فاتورة
> - صورة تواصل اجتماعي
> ⇒ العميل **ينزّلها ويستخدمها**. WASL بقت جزء من مؤسسته فعلاً، مش بس في لوحة.

**ⓔ — هوية الموظف الذكي**
> الموظف اللي العميل شايفه (اسمه + صورته + نبرته) = **هوية العميل**. WASL تظهر سطر تقني صغير في «عن الموظف». ده أقوى محرّك للإحساس بـ«صُمم خصيصاً لي».

### ٨.٣ ⭐ الضمان ضد «شعارات جنب بعض»

| الفحص | العتبة |
|---|---|
| في أي سطح: هل لوحدة لون العميل تاخد المساحة البصرية الأكبر؟ | نعم — العلامة الغالبة هي العميل |
| هل WASL بتظهر كـ«مُزوّد خدمة» مش كـ«منافس»؟ | نعم |
| هل ممكن نعمل ده الشعار من غير اسم WASL؟ | ⛔ لأ — وده معيار الفشل |
| نسبة المساحة البصرية للعلامة الغالبة | ≥ ٦٠٪ |

## ٩. الإعدادات واللغات وتجربة الاستخدام

### ٩.١ مبدأ «السهل الممتنع»

> **القوة تحت، البساطة فوق.** المستخدم العادي ما يشوفش لوحة تحكم معقّدة. المستخدم المتقدم يلاقي كل حاجة — بس بعد طبقة.

```
الشاشة الافتراضية: ٣–٥ أسئلة، مع «تفاصيل» مخفي
الطبقة الثانية:      إعدادات النشاط (ساعات · نبرة · حدود)
الطبقة الثالثة:     إعدادات متقدمة (أدوات · تسعير · تكاملات) + بحث
```

**قاعدة الحقول**: كل حقل = **سؤال بلغة العميل** + **مثال** + **الأثر على السلوك**.
⛔ **ممنوع** حقل بلا شرح. ⛔ **ممنوع** مصطلح تقني بدون ترجمة.

### ٩.٢ اللغات

- ✅ عربي + إنجليزي في **اللوحتين** + **العميل** + **الإيميلات** + **قوالب واتساب**.
- ✅ تبديل في الإعدادات + قائمة الحساب + **أول زيارة تسأل**.
- ✅ **الافتراضي حسب بلد العميل** (مصر⇒عربي · خليجي⇒عربي + إنجليزي كخيار).
- ✅ **RTL/LTR كامل** (§٣.٧).
- ✅ **لا إعادة تحميل** عند التبديل (i18n runtime).

### ٩.٣ تجربة التليفون والكمبيوتر

- **التابلت 390/768** هو الأساس (زي الـOCTA) — مش الموبايل.
- ⛔ لا تمرير أفقي على أي شاشة. ⛔ لا جدول بأعمدة كتير على الموبايل ⇒ **بطاقات**.
- **الشاشة الأولى = «اليوم»** (٦ بطاقات) — مش Dashboard بـ charts.
- ⛔ **إيميل/رقم واحد** لكل عميل في كل خطوة.

### ٩.٤ PWA — بشروط النجاح (بناءً على درس OCTA)

| العنصر | القرار |
|---|---|
| `manifest.json` | ✅ كامل (name · icons 192/512 · display standalone · dir · lang) |
| Service Worker | ⛔ **مش زي OCTA القديم**. ⚠️ الدرس: لازم يتعمل صح من الأول |
| الكاش | **الأصول الساكنة بس** (JS/CSS/خطوط/أيقونات). ⛔ **مفيش** كاش لـAPI |
| البيانات | Network-first دايماً. ⛔ **مفيش** تخزين محادثات أو عملاء على الجهاز |
| تسجيل الخروج | ⛔ يمسح كل الـcache + كل الـstorage |
| التحديث | `skipWaiting` + `clients.claim` ⇒ التحديث فوري |
| iOS | `apple-touch-icon` + `apple-mobile-web-app-capable` (مطلوب — iOS مش strict زي Android) |
| **اختبار تسريب** | ⛔ **release gate**: بعد تسجيل الخروج على جهاز مشترك ⇒ صفر بيانات شخصية ظاهرة |

### ١٠.١ معايير القبول — لكل مرحلة (hard gates)

**المرحلة ١ — النواة**
```
✅ جدولان مستأجران · ٥٠ محاولة وصول متعمّدة من A لـB ⇒ صفر تسريب
✅ نفس المكوّنات تُعرض ar (RTL) و en (LTR) ⇒ ٠ فرق بصري
✅ commit ⇒ preview URL ⇒ الاختبارات خضراء (CI)
✅ ٣ مستخدمين حقيقيين في الشركة يدخلوا من غير تدريب
```

**المرحلة ٢ — محرك الموظف الذكي**
```
✅ محادثة ٣٠ دور · السياق متّسق · صفر تناقض
✅ ١٠٠ سؤال من معرفة النشاط ⇒ صفر معلومة مخترعة
✅ ٢٠ سؤال خارج النطاق ⇒ ٢٠/٢٠ رفض + تصعيد
✅ كل أداة × كل دور ⇒ المنع شغّال (مصفوفة كاملة)
✅ زمن الرد p95 < ٣ ثوانٍ
```

**المرحلة ٣ — المعالج + الحزمة**
```
✅ عميل جديد من الصفر للتشغيل ≤ ٦٠ دقيقة (المالك هو اللي بيعمله)
✅ الحزمة بتتولّد إعدادات · مش بيانات خام
✅ محادثة اختبارية قبل التفعيل ≥ ٨٠٪ دقة
✅ حزمة «مطعم»: ٥٠ سؤال × ≥ ٨٥٪ دقة
```

**المرحلة ٤ — القناة + اللوحة**
```
✅ رسالة واتساب حقيقية ⇒ رد < ٣ ثوانٍ باللهجة الصح
✅ العميل ياخد المحادثة ⇒ الذكاء الاصطناعي يوقف فوراً + العامل يشوف السياق كامل
✅ طلب/حجز من المحادثة ⇒ ظاهر في اللوحة
✅ ٥ مستخدمين حقيقيين بيخلّصوا مهماتهم من اللوحة من غير تدريب
```

**المرحلة ٥ — الهوية + PWA**
```
✅ العميل يرفع شعاره ⇒ لون الواجهة كله يتغيّر لوحده (من غير مطوّر)
✅ حزمة الهوية اتولّدت (lockup + فاتورة + واتساب + أفاتار)
✅ اللوحتين بيتثبتوا PWA على Android + iOS
✅ ⛔ اختبار التسريب: بعد logout على جهاز مشترك ⇒ صفر بيانات شخصية
```

**المرحلة ٦ — المنصة + الفوترة**
```
✅ Central Admin ينشئ عميل ويشغّله من غير مطوّر
✅ تكلفة كل محادثة ظاهرة لكل عميل/قطاع/ميزة · مطابقة فاتورة المزوّد ±٥٪
✅ كل إجراء إداري في سجل التدقيق (مين · إمتى · إيه · النتيجة)
✅ kill switch: تعطيل موظف عميل واحد < ٦٠ ثانية · ما يأثرش على غيره
```

**المرحلة ٧ — التوسّع**
```
✅ ١٠ عملاء · ٣ أنشطة مختلفة · كلهم من الحزم (بدون كود مخصص)
✅ إضافة نشاط جديد بحزمة كتبها غير مطوّر
✅ اختبارات العزل خضراء على كل العملاء
✅ ٩٩٫٩٪ توفر مقيسة على ٣٠ يوم
✅ كل بيانات عميل قابلة للحصر في منطقة (مستند + مُختبَر)
```
