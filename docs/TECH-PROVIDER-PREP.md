```
   ┌────────────────────────────────────────────────────────────────┐
   │                    WASL AI  (المنصّة)                           │
   │  ┌──────────────┐  ┌──────────────┐  ┌────────────────────┐   │
```

> ⭐ **حدود الثقة (Trust boundaries)**: ⭐ **(١)** حدّ Meta ⭐ **(٢)** حدّ WASL ⭐ **(٣)** حدّ مزوّد AI ⭐ **(٤)** حدّ الاستضافة ⭐ **(٥)** حدّ العميل المنشئ.
> ⭐ **❓ غير محسوم**: ⭐ **هل WASL «متحكّم» أم «معالِج» في البيانات — قرار قانوني للمحلّي (Q-L1) ⇒ ولا يُبنى عليه أي تفصيلة تنفيذية في هذا القسم.**

### ١.٢ تدفّق تسجيل العميل (Overview)

```
المالك (منصة) ──▶ يختار العميل المنشئ ──▶ [Embedded Signup: توجيه العميل]
                                              │
        العميل يوافق على ربط WABA/رقم ◀───────┘
                                              │
                          [Webhook: تجهيز WABA/الرقم] ──▶ تخزين tenant_id
```

### ١.٣ تدفّق الرسالة (من المتجر إلى العميل)

```
1) العميل ينشئ محادثة → رسالة تصل إلى قناة Meta
2) Meta → webhook (حدث رسالة واردة) إلى WASL
3) WASL: تحقّق التوقيع → منع التكرار → enrich بـ tenant_id
4) WASL: تصنيف (رد آلي / إسناد لموظف / تحديث CRM)
5) WASL: رد آلي (اختياري) → إرسال عبر Cloud API
6) Meta → webhook (حالة التسليم) → تحديث حالة الرسالة في السجل
```

> ⭐ **مصدر الأطوار ١–٨ (الاستقبال · التخزين · المعالجة الآلية · الإسناد البشري · التسويق · الاحتفاظ · التدريب · لا بيانات حقيقية)**: ⭐ `docs/LEGAL-PACKAGE.md` §٢.٣ ⇒ ⭐ **وهذا التوثيق الهندسي لا يغيّرها ولا يحسمها.**

## ٢. ⭐ توصيف واجهات API والعقود المقترحة

> ⭐ **⚠️ هذا القسم مسودّة توصيف (لا مرجع تنفيذي)** ⇒ ⭐ **لأن صفحات التوثيق الرسمية (S1 · S2) لم تُفتح (HTTP 400) ⇒ ⇒ ⇒ كل اسم نقطة أو بارامتر أو رمز خطأ ⭐ «يُثبَّت من التوثيق الرسمي قبل التنفيذ».**
> ⭐ **المصدر المرجعي المطلوب**: ⭐ `https://developers.facebook.com/docs/whatsapp/cloud-api` (وS1/S2 أعلاه) — ⭐ **وحالة الفتح تُسجَّل في `docs/WHATSAPP-PATH-RESULT.md` §٩.**

### ٢.٣ نموذج الطلب/الاستجابة (شكل عام — بلا قيم مُختلَقة)

**طلب إرسال (شكل مقترح):**
```json
{
  "messaging_product": "whatsapp",
  "recipient_type": "individual",
  "to": "<رقم المستقبِل>",
  "type": "<text | template | image | ...>",
  "text": { "body": "<نص>" }
}
```
**استجابة (شكل مقترح):**
```json
{
  "messaging_product": "whatsapp",
  "contacts": [ { "input": "<رقم>", "wa_id": "<معرّف>" } ],
  "messages": [ { "id": "<معرّف الرسالة>" } ]
}
```
> ⭐ **⚠️ القيم بين الأقواس حواجز تُملأ من بيانات العميل ⇒ ولا تُكتب قيم تجريبية حقيقية في أي ملف.**

### ٢.٤ نموذج الأخطاء (فئات — الأكواد تُثبَّت)

| ⭐ الفئة | ⭐ المعنى | ⭐ السلوك المقترح | ⭐ ملاحظة |
|---|---|---|---|
| ⭐ **عابر (transient)** | ⭐ الشبكة · Timeout · 5xx | ⭐ إعادة محاولة بتباعد متزايد ضمن ميزانية | ⚠️ **حدود المحاولات تُضبط بعد قياس** |
| ⭐ **دائم (permanent)** | ⭐ 4xx (بخلاف حدود المعدل) | ⭐ لا إعادة محاولة · تُسجَّل الحالة | ⚠️ **أكواد تُثبَّت** |
| ⭐ **حدّ معدّل (rate limit)** | ⭐ تجاوز حدّ الإرسال | ⭐ احترام رأس إعادة المحاولة | ❓ **رأس الـRetry-After: غير محسوم ⇒ يُثبَّت** |
| ⭐ **تفويض** | ⭐ رمز منتهي أو صلاحية ناقصة | ⭐ تجديد + إعادة محاولة واحدة | ⚠️ **تصميم** |
| ⭐ **غير معروف** | ⭐ لم يُصنَّف | ⭐ يُسجَّل كاملاً (مع إخفاء البيانات الحسّاسة) | ⚠️ **تصميم** |

> ⭐ **❓ غير محسوم**: ⭐ **جدول الأكواد الفعلي وحقول الأخطاء في استجابة Meta ⇒ ⇒ ⇒ يُثبَّت من التوثيق قبل التنفيذ.**

### ٢.٥ قواعد عامة للتعاقد الداخلي (WASL ⇄ الكيانات)

- ⭐ **كل عملية تطلب `tenant_id` صريحاً** ⇒ ⭐ **ولا تُشتق من سياق ضمني ⇒ ⭐ **حدّ خطأ واحد** = تسريب بيانات مستأجر (لذلك العزل §٥ ليس اختيارياً).**
- ⭐ **لا تُمرَّر بيانات مستأجر في مسار URL** ⇒ ⭐ **وتُستخدم معرّفات في سجلّ واحد لكل عملية (correlation id).**
- ⭐ **⛔ لا سرّ في المستودع** ⇒ ⭐ **المفاتيح من متغيّرات البيئة فقط (وتنطبق قاعدة §٦.١).**


## ٣. تصميم تدفق Embedded Signup على الورق

> هذا القسم توصيف ورقي لمجرى تسجيل العميل المنشئ. لم يُنفَّذ أي جزء منه، ولم يُجرَ أي اتصال بواجهة برمجية حقيقية. أسماء الحقول ونقاط النهاية في هذا القسم أسماء مقترحة، وتُثبَّت من التوثيق الرسمي قبل أي كتابة كود.

### ٣.١ الغرض والنطاق

الهدف من هذا المجرى أن يربط العميل المنشئ حسابه على منصة واتساب بنفسه، بحيث تبقى أصوله (الرقم والحساب الإعلاني والرسائل) في حيازته هو. هذا يفي بغرض المسار المقترح «شريك تقني مستقل مع التسجيل المدمج» المذكور في بطاقة القرار.

النطاق: تسع خطوات تغطي من لحظة فتح العميل للمنصة إلى لحظة اعتماد ربط الحساب، مع تحديد حالات الفشل في كل خطوة. ما لا يشمله هذا القسم: اختيار طريقة الدفع، وإعدادات الفوترة، وأي تعامل مع حساب في Meta. هذه أمور متروكة للقرار أو لخطوة لاحقة.

### ٣.٢ الخطوات التسع

| # | الخطوة | الفاعل | المخرج | حالة الفشل |
|:-:|---|---|---|---|
| ١ | فتح المضيف للتسجيل المدمج | العميل | شاشة ربط | تعذّر تحميل المكوّن |
| ٢ | إدخال رقم الهاتف | العميل | رقم مُتحقَّق منه | رقم غير صالح أو مكرَّر |
| ٣ | التحقق من الرمز | مزوّد التوفيق | رمز مؤكَّد | رمز خاطئ أو منتهي |
| ٤ | إنشاء أو اختيار الحساب الإعلاني | مزوّد التوفيق | معرّف الحساب | لا يوجد حساب لهذا الرقم |
| ٥ | منح صلاحيات التطبيق | العميل | موافقة صريحة | رفض المستخدم أو انتهاء المهلة |
| ٦ | التحقق من ساعات العمل وهوية العلامة | مزوّد التوفيق | بيانات الملف | تعذّر التحقق |
| ٧ | إنشاء رمز وصول مؤقت | مزوّد التوفيق | رمز وصول | فشل الإصدار أو انتهاء الصلاحية |
| ٨ | اختبار الاتصال | مزوّد التوفيق | نتيجة اختبار | تعذّر الاتصال |
| ٩ | تخزين الربط وعرض النتيجة | مزوّد التوفيق | سجل ربط | فشل التخزين |

```
  |                    |<-- تأكيد الربط -------|                 |
  |<-- حالة الربط -----|                       |                 |
```

**ملاحظات على المخطط:**

- خطوات التحقق (٣) وموافقة الصلاحيات (٥) تتم في واجهة Meta نفسها، لا في واجهتنا. هذا مقترح لأن الأصول تبقى في حيازة العميل، وهو جوهر معيار «حساب العميل» في مسار الشريك التقني.
- رمز الوصول المؤقت (٧) هو الوسيط الوحيد بين مزوّد التوفيق وMeta. لا يُطلب من العميل أي رمز دائم.
- التخزين (٩) هو نقطة الفشل الوحيدة التيلدينا فيها بيانات العميل. لازم أن يكون قابلاً لإعادة التنفيذ بدون فقدان ما سبق إنجازه.

### ٣.٤ حالات الفشل الشائعة ومعالجتها المقترحة

| الحالة | العلامة | المعالجة المقترحة | أثر على المستخدم |
|---|---|---|---|
| العميل يرفض الصلاحيات | خطأ موافقة | إعادة المحاولة مع توضيح الصلاحيات المطلوبة | لا يُسجَّل ربط |
| رمز التحقق منتهي | خطأ رمز | طلب رمز جديد بحدّ المحاولات | لا يُسجَّل ربط |
| الحساب الإعلاني غير موجود | خطأ إنشاء | فتح مسار إنشاء الحساب المدمج | خطوة إضافية |
| فشل إصدار رمز الوصول | خطأ خادم | إعادة المحاولة بتأخير متزايد | لا يُسجَّل ربط |
| انقطاع الشبكة أثناء الاختبار | مهلة | إعادة الاختبار حتى ٣ مرات | الربط معلّق |
| تعذّر التحقق من البيانات | ملف ناقص | طلب استكمال البيانات من العميل | الربط معلّق |

**قاعدة عامة:** أي خطوة تفشل لا تُحذف سجلّها. تُحفظ الحالة الفاشلة مع سببها حتى يمكن استئنافها لاحقاً بدل إعادة العملية من الصفر.


## ٤. توصيف Webhooks وآليات استقبال الرسائل

> توصيف ورقي. لم يُنفَّذ ولا نُظِّرت بيئة اختبار. أسماء الأحداث كما وردت في مخططات §١ محفوظة بوصفها أسماء مقترحة.

### ٤.١ الأحداث المتوقعة

| # | الحدث | المعنى المقترح | المصدر | الأولوية |
|:-:|---|---|---|:-:|
| ١ | رسالة واردة | استلام رسالة من مستخدم | Meta | عالية |
| ٢ | حالة الرسالة | تسليم أو فشل أو انتهاء صلاحية | Meta | عالية |
| ٣ | تسجيل رقم | ربط رقم بالحساب الإعلاني | Meta | عالية |
| ٤ | جودة الحساب | تغيّر في حالة الحساب أو التقييم | Meta | متوسطة |
| ٥ | تغيّر الصلاحيات | سحب أو تعديل صلاحيات التطبيق | Meta | عالية |
| ٦ | انتهاء صلاحية الرمز | تعطّل تدفّق الرسائل | Meta | عالية |

### ٤.٢ التحقق من التوقيع

- كل طلب وارِد يجب أن يُفحص قبل أي معالجة: **المصدر** (IP/المصدر الرسمي) و**التوقيع** (HMAC على الحمولة الخام بالسرّ، مقارنة بزمن ثابت لمنع هجمات التوقيت).
- عند فشل التحقق: **تُرفض الحمولة بالكامل** ولا تُسجَّل كرسالة، مع تسجيل محاولة فقط (بلا محتوى الحمولة).
- السرّ يُدار كمتغيّر بيئة ولا يظهر في السجلّات ولا في المستودع.
- المقارنة تُجرى بالبايت الخام لا بالحمولة المُحلَّلة، وإلا اختلف التوقيع.


### ٤.٣ منع التكرار (Idempotency)

- **معرّف الحدث** هو مفتاح منع التكرار: كل معالجة تبدأ بالبحث عن المعرّف في جدول معالَجات.
- لو المعرّف موجود: تُسجَّل «محاولة جديدة» بلا معالجة ثانية، وتُعاد الاستجابة نفسها.
- الجدول يُحتفظ به مدة أطول من مدة إعادة المحاولة القصوى عند Meta (اقتراح: ٧ أيام).
- على مستوى الرسائل نفسها: يُفحص معرّف الرسالة الواردة قبل الإدراج، لأن Meta قد تعيد إرسال نفس الحدث عند فشل الاستجابة.

### ٤.٤ التخزين ومدة الاحتفاظ

| البيانات | ما يُخزَّن | مدة مقترحة | ملاحظة |
|---|---|---|---|
| استقبال الرسالة | الحمولة والوسائط والمعرّفات | حسب سياسة العميل (§٦.٤) | المحفظة مش ما نشتغلش عليها في هذا الملف |
| سجلّ المعالجة | معرّف الحدث ونتيجته | ٧ أيام على الأقل | لمنع التكرار |
| سجلّ الأخطاء | نوع الخطأ والرمز | ٣٠ يوماً | بلا محتوى الرسالة |
| بيانات الحساب | معرّف الحساب الإعلاني واسمه | مدى العلاقة | لا يُحفظ الرمز الدائم بصيغة مقروءة |
| وسائط | الملف نفسه | حسب سياسة العميل | في مخزن معزول |

**قاعدة:** ما لا يُحفظ لا يحتاج حماية. أي حقل ليس لازماً للخدمة يُحذف من المخطط قبل التنفيذ.

### ٤.٥ إعادة المحاولة والتعامل مع الأخطاء

- عند فشل الاستجابة: تعيد Meta الإرسال. استراتيجيتنا: **إجابة ناجحة بسرعة** ثم **معالجة غير متزامنة**، حتى لا يتحمّل Meta فشلنا.
- أخطاء الدائمة (حمولة غير صالحة، توقيع مرفوض) تُرفض مباشرة ولا تُعاد.
- أخطاء مؤقتة (قاعدة البيانات متوقفة) تُخفَّض الاستجابة إلى 5xx حتى تعيد Meta الإرسال.
- حدّ أقصى للمحاولات داخل التطبيق: ٥، ثم تحويل الحالة إلى «فشل مُعالَج» مع إشعار الدعم.

### ٤.٦ ما يُخزَّن وما لا يُخزَّن صراحةً

**يُخزَّن:** معرّفات الحساب والرسالة، نص الرسالة كما وصل، حالة التسليم، أوقات المعالجة.

**لا يُخزَّن:** رمز العميل الدائم بصيغة مقروءة، مفاتيح التوقيع داخل السجلّات، وسائط العميل في جداول المعالجة (تذهب إلى المخزن المنفصل).


## ٥. تصوّر العزل بين الشركات وصلاحيات الوصول

> ⛔ **تنبيه معماري:** العزل على مستوى الصفوف (RLS) في `Postgres` يعتمد على `DR-4` وهو **🔵 غير معتمد**. كل ما في هذا القسم **تصوّر** يعتمد على افتراض معماري غير معتمد، ولا يُبنى قبل صدور قرار المالك.

### ٥.١ الطبقات الثلاث المقترحة

| الطبقة | الغرض | الآلية المقترحة | حالة الاعتماد |
|:-:|---|---|---|
| ١ | عزل البيانات | كل صف يحمل `tenant_id`، والاستعلام لا يمرّ إلا بمُرشِّح إلزامي | افتراض معماري (DR-4 غير معتمد) |
| ٢ | عزل الوصول | الدور يُحدَّد داخل طبقة التطبيق قبل بناء الاستعلام | قابل للتنفيذ بلا اعتماد |
| ٣ | عزل التشغيل | حاوية مستقلة لكل بيئة (تطوير · اختبار · إنتاج) بلا بيانات مشتركة | قابل للتنفيذ بلا اعتماد |

**ملاحظة على الطبقة ١:** هذه الطبقة هي الأهم، وهي أيضاً الأكثر اعتماداً على قرار غير صادر. لو اعتُمد العزل على مستوى التطبيق وحده دون طبقة البيانات، فأي استعلام مكتوب خطأً يسرّب بيانات مستأجر آخر. لذلك يُنصح بأن بأن تُحسم هذه الطبقة أولاً.

### ٥.٢ جدول الصلاحيات المقترح

| الدور | القراءة | التعديل | الإرسال | قراءة التقارير | إدارة الربط | الدعم |
|---|---|:-:|:-:|:-:|:-:|:-:|
| مالك الشركة | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| مدير الشركة | ✅ | ✅ | ✅ | ✅ | — | — |
| موظّف خدمة عملاء | ✅ | محدود | ✅ | محدود | — | — |
| محاسب | — | — | — | ✅ فقط | — | — |
| مشرف داخلي | ✅ قراءة فقط | — | — | ✅ | ✅ | ✅ |
| مهندس (تشخيص) | ✅ قراءة فقط | — | — | محدود | — | ✅ |


### ٥.٣ سيناريو الدعم الداخلي (الأكثر حساسية)

المشكلة: الدعم الداخلي يحتاج قراءة بيانات مستأجر عند بلاغ، لكن هذا كسر للعزل.

المقترح: **وصول مع الوقت والمدى**.
- كل طلب دعم يفتح **نافذة وصول** محدودة: شركة واحدة + مدّة محددة (اقتراح: ساعة) + سبب مكتوب.
- كل قراءة داخل النافذة تُسجَّل في سجلّ تدقيق باسم الموظف وسبب الطلب.
- النافذة تنتهي تلقائياً ولا تُجدَّد إلا بطلب صريح.
- لا يمكن التصفّح الحر داخل النافذة: فقط ما هو مرتبط بالبلاغ.

**البديل المرفوض:** حساب «دعم» دائم على مستوى قاعدة البيانات ⇒ لا يمكن تتبع من قرأ ماذا، ويُلغي معنى العزل.

### ٥.٤ قواعد إلزامية قبل أي تنفيذ

1. كل استعلام على بيانات المستأجر يجب أن يحمل `tenant_id` في شرطه، ويُرفض الاستعلام الناقص.
2. لا يوجد مسار إداري يصل إلى جدول الرسائل مباشرة.
3. الاختبارات العزل (٢٢ سيناريو في `REVIEWS/R007-r006-review-remediation.md` §3) هي معيار القبول لأي تنفيذ مستقبلي.
4. أي استثناء للعزل يُكتب كقاعدة صريحة في الكود مع اسم العميل وسببه ومدّته.

### ٥.٥ ما هو غير محسوم

- ❓ هل العزل على مستوى الصفوف هو الخيار المعتمد، أم أن التصميم يُبنى على قواعد بيانات منفصلة لكل شركة؟
- ❓ هل يمرّ الدعم الداخلي على نفس طبقة التطبيق أم عبر قناة منفصلة؟
- ⛔ هذه أسئلة معمارية تُحسم بقرار المالك ولا تُحسم هنا.


## ٦. متطلبات الأمان وحماية البيانات

> متطلبات مقترحة للكتابة في وثيقة المتطلبات قبل التنفيذ. لم تُطبَّق ولم تُختبر.

### ٦.١ الأسرار (Secrets)

| القاعدة | التفصيل |
|---|---|
| المصدر | متغيّرات بيئة أو مخزن أسرار مُدار فقط |
| الحظر | ⛔ لا سرّ في المستودع ولا في سجلّات التطبيق ولا في صورة الحاوية |
| التدوير | عند تسرّب مشتبه به، تدوير فوري وإبطال كل جلسة مشتقة |
| الصلاحية | كل سرّ يُقرأ عند الحاجة فقط، ولا يُمرَّر كوسيط في الاستدعاءات |

### ٦.٢ التشفير

- **النقل**: TLS إلزامي على كل النداءات الخارجية والداخلية.
- **التخزين**: حقول محدّدة (معرّف الحساب، رمز الوصول، معرّف العميل) مشفّرة على مستوى الحقل.
- **الوسائط**: تُخزَّن في مخزن خاص، وتُسلَّم عبر رابط موقّع محدود الصلاحية.

### ٦.٣ تصغير البيانات (Data Minimization)

- لا يُطلب من العميل إلا ما تحتاجه الخدمة فعلاً: الاسم، الهاتف، البريد، اسم الشركة، الفئة.
- لا يُجمع أي بيانات عميل في التحليلات إلا بعد تجميعها وإخفاء المعرّفات.
- حقول Telegram أو الدعم تُحذف من نسخة الإنتاج.


### ٦.٤ الاحتفاظ بالبيانات (Retention)

| الفئة | المدة المقترحة | ملاحظة |
|---|---|---|
| سجلّات الوصول (من دخل إمتى) | ١٢ شهراً | مرجع تشغيلي |
| بيانات الرسائل | حسب عقد العميل | تُحذف عند انتهاء العقد + مدة سماح |
| وسائط العميل | نفس سياسة الرسائل | — |
| سجلّ التدقيق | ٢٤ شهراً | لا يُحذف إلا بقرار موثّق |
| بيانات الحساب (الحساب الإعلاني) | مدى العلاقة | تُحذف عند فكّ الربط + ٣٠ يوماً |
| رموز الوصول | عمر الرمز | تُبطَل فوراً عند سحب الصلاحيات |

**قاعدة الحذف:** حذف العميل يجب أن يكون عملية قابلة للتحقق (تقرير حذف بمعرّفات ما حُذف ومتى)، لا مجرّد أمر `DELETE`.

### ٦.⑤ سجلّ التدقيق

كل عملية حسّاسة تُسجَّل: من، ماذا، متى، أي شركة، أي نتيجة. يشمل ذلك: الدخول، تصدير بيانات، تعديل صلاحيات، فتح نافذة دعم، طلب تصدير، حذف.

### ٦.⑥ المعالجات الفرعية (Subprocessors)

- تُوثَّق قائمة المعالجين (استضافة · تخزين · بريد · تحليلات) وتُحدَّث عند أي تغيّر.
- ⛔ إضافة معالج جديد = تغيير تعاقدي يستدعي إخطار العميل مسبقاً.
- ❓ لم تُحدَّد بعد القائمة الفعلية — تعتمد على قرار البنية التحتية.

### ٦.٧ الاستجابة للحوادث

- لكل حادثة أمنية: تصنيف (خطأ · حادث · اختراق)، ومالك محدّد، ومهلة استجابة.
- في حالة اختراق افتراضي: إبطال كل الرموز، إيقاف مسار استقبال Webhook المتأثر، إخطار كل شركة متأثرة حسب العقد.
- ⛔ لا يوجد اليوم بروتوكول حادث مكتوب أو مُختبر. هو بند من بنود التحضير البرمجي (§٢ من وثيقة النطاق).


## ٧. سيناريوهات الاختبار المقترحة (دون تنفيذ)

> ⛔ **لم يُنفَّذ أي سيناريو من هذه القائمة.** هذه مواصفات اختبار للكتابة لاحقاً، لا اختبارات مُنفَّذة ولا نتائج. عدد الاختبارات المُنفَّذة سابقاً في هذا المشروع: صفر.

### ٧.١ أربعة عشر سيناريو وظيفي

| # | السيناريو | المدخل | النتيجة المتوقّعة |
|:-:|---|---|---|
| ١ | تسجيل رقم جديد | رقم غير مرتبط | ربط ناجح + رمز وصول |
| ٢ | إعادة ربط رقم مرتبط | نفس الرقم لنفس الشركة | رفض + رسالة واضحة |
| ٣ | ربط رقم لحساب إعلاني موجود | حساب بنفس الشركة | نجاح بدون إنشاء حساب جديد |
| ٤ | ربط رقم لحساب مستأجر آخر | حساب شركة أخرى | رفض تام |
| ٥ | رسالة واردة | webhook صحيح | تخزين + إشعار للعميل |
| ٦ | رسالة مكرّرة | نفس معرّف الحدث مرتين | تخزين واحد فقط |
| ٧ | webhook بتوقيع خاطئ | توقيع غير صحيح | رفض + سجل محاولة |
| ٨ | webhook بلا توقيع | طلب بلا رأس التوقيع | رفض |
| ٩ | إعادة إرسال من Meta | نفس الحدث بعد استجابة فاشلة | لا معالجة مزدوجة |
| ١٠ | خطأ في قاعدة البيانات | القاعدة متوقفة | استجابة 5xx + إعادة إرسال آمنة |
| ١١ | عميل يسحب الصلاحيات | سحب من Meta | إبطال الرمز + إيقاف المسار |
| ١٢ | انتهاء صلاحية الرمز | رمز منتهي | إعادة تدفّق ربط |
| ١٣ | استعلام عزل | استعلام بلا `tenant_id` | رفض من طبقة البيانات |
| ١٤ | نافذة دعم | طلب دعم على شركة واحدة | قراءة محدودة + تسجيل |


### ٧.٢ خمسة سيناريوهات فشل

| # | السيناريو | Failure | النتيجة المتوقّعة |
|:-:|---|---|---|
| ١ | انقطاع الشبكة أثناء التسجيل | عطل في الطبقة الوسيطة | عدم حفظ ربط ناقص + إمكانية الاستئناف |
| ٢ | انتهاء مهلة الموافقة | مهلة منتهية | لا ربط + إرشاد العميل لإعادة المحاولة |
| ٣ | رفض المستخدم للصلاحيات | رفض صريح | رسالة صريحة + تسجيل السبب |
| ٤ | ازدواج الطلب | طلب متزامن | ربط واحد فقط (قفل على مستوى العميل) |
| ٥ | مهلة قاعدة البيانات | مهلة منتهية | تراجع تلقائي + تنبيه بعد ٥ محاولات |

### ٧.٣ معيار القبول المقترح

- كل سيناريو من الأربعة عشر ينجح في بيئة الاختبار، أو يُوثَّق سبب التعذّر.
- سيناريوهات العزل (١٣) و(١٤) لا تُعتبر ناجحة إلا إن **فشلت** الاختبارات المعاكسة: أي استعلام يعيد بيانات شركة أخرى = فشل أمني حتى لو كان الاختبار الموجب ناجحاً.
- ⛔ هذه المعايير تُعتمد فقط بعد صدور تصريح تنفيذ (§٢ من وثيقة النطاق).
