### ⭐ ٤ — `limit` و`offset` بلا فحص رقمي في مسارين من ثلاثة ⭐ **متوسطة · مؤكد**

| | |
|---|---|
| **المكان** | ⭐ `server/api/server.ts:1632-1633` (مسار التذاكر) ⭐ و`server/api/server.ts:2557-2558` (مسار الوارد) |
| **المقابل السليم** | ⭐ `server/api/server.ts:2294-2295` (مسار الـCRM) ⭐ فيه `Number.isFinite(limit) ? limit : 25` ⭐ ⇒ ⇒ **الأنماط الثلاثة ليست متسقة**. |
| **السبب** | ⭐ `Number('abc')` = `NaN` ⭐ و`Math.max(1, Math.min(NaN, 200))` = `NaN` ⭐ ⇒ ⇒ و`NaN` يذهب إلى PostgreSQL كمعامل ⭐ ⇒ ⇒ فيرفضه المحرك ⇒ ⇒ **الطلب الخبيث يصير خطأ قاعدة بيانات لا جواب نظيف** ⭐ (والقَصّ في `server/tickets/queries.ts:211-212` لا ينقذ ⭐⇒ `Math.max` مع `NaN` تُعيد `NaN`). |
| **الدليل الحيّ** | ⭐ `GET /api/tickets?limit=abc` ⇒ ⭐ `400` بجسم `{"code":"22P02","message":"invalid input syntax for type bigint: \"NaN\""}` ⭐ ⭐ (وهذا ⭐ الملاحظة ١ ⭐ مثالاً حيّاً: خطأ مدخل ينتج **نصاً خاماً**). ⭐ وبالمقابل `GET /api/crm/customers?limit=abc` ⇒ ⭐ `200` بالقيمة الافتراضية ⭐ ⇒ ⇒ **الفرق في الكود واضح**. ⭐ وكذلك `GET /api/inbox/conversations?offset=abc` ⇒ ⭐ `400`. |
| **الأثر** | ⭐ **خلط مدخلات غير موثوقة بخطأ داخلي** ⭐ ⇒ بدل جواب «الحدّ غير صالح» يصير جواب «خطأ في القاعدة» ⭐ ⇒ ⭐ وهذا ما يجعل ⭐ **تنبيه المراقبة (إن وُجد) لا يفرّق بين خطأ مدخل وخطأ خادم** ⭐ ⇒ ويكشف ⭐ الملاحظة ١ ⭐. |
| **الإصلاح المقترح** | ⭐ نفس حرس المسار الثالث ⭐ بالضبط ⭐ في السطرين 1632-1633 و2557-2558: ⭐ `Number.isFinite(...) ? ... : <default>` ⭐ (ويمكن نزع `Math.max/Math.min` من `server/tickets/queries.ts:211-212` ليبقى الحدّ في طبقة الطلب ⭐ ⇒ **حدّ واحد لا ثلاثة**). |
| **مؤكد؟** | ⭐ **مؤكد** — سلوك مقيس على الخادم الحيّ ⭐ (تذاكر ووارد ⇒ 400 ⭐ CRM ⇒ 200). |
